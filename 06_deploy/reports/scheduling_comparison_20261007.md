# 调度参数对照测试（2026-10-07）

在 RDK-X5 `192.168.1.12` 上测试了建议配置。新配置降低了 BPU API 耗时和端到端的合并 P95/P99，但 CPU 后处理长尾增加，尚未消除所有超时尖峰。保留现有脚本默认值，新配置可通过环境变量启用；本次只调整启动参数，没有修改可执行文件。

## 方法

- 默认 A：`QUEUE_CAPACITY=2 CAPTURE_CPUS=2 INFERENCE_CPUS=3 RT_PRIORITY=20`。
- 建议 B：`QUEUE_CAPACITY=1 CAPTURE_CPUS=2-3 INFERENCE_CPUS=0-7 RT_PRIORITY=0`。
- 顺序 A/B/B/A/A/B，每次 300 帧，两组各 900 帧，目标 15 Hz，`WARMUP=5`。
- 两组使用同一模型和程序，保留 DEBUG 日志、逐帧 JSON/PGM 写盘。板端全部 6 次均 `produced=300 completed=300`，发送/接收帧 ID 一致。
- `WARMUP=5` 仅丢弃摄像头帧，并没有运行模型。为统一比较，另从每轮统计中排除前 5 个实际推理样本，合并样本每组 885 帧；JSON 同时保存含启动帧的全量统计。百分位采用线性插值。
- 运行中从 `/proc` 确认默认推理内部线程均在 CPU3/SCHED_RR(20)，新配置允许 CPU0–7/SCHED_OTHER。状态快照中 BPU 约 996 MHz，CPU governor 为 schedutil；这不是连续频率监测。
- 本次现场画面检测数均为 0，不能代表密集检测目标下的 NMS 开销。

## 对原因的判断及计时限制

1. `bpu_ms` 覆盖 `hbDNNInfer + hbDNNWaitTaskDone + hbDNNReleaseTask`，包含 SDK 提交、任务等待和线程调度，不是纯 BPU 硬件执行时间。此前用 `37.4 ms × 15 Hz ≈ 56%` 表述为 BPU 实际利用率不准确，只能作为 API 墙钟耗时预算比例，尚未采集硬件忙碌率。
2. 新配置降低了 BPU API P95，但同时改动队列、CPU 亲和性和调度策略，不能把改善唯一归因于某个参数。BPU IRQ 在 CPU0 也不能单独证明跨核唤醒就是根因；DDR 争用同样未被这次测试验证。
3. 默认第 4 轮 frame=272 的 e2e 为 299.935 ms，但 bpu=35.617、post=4.269 ms；建议第 3 轮 frame=534 的 e2e 为 123.350 ms，但 bpu=35.771、post=4.234 ms。这两个大尖峰主要在 BPU/后处理计时之外，不能归因于 BPU 算力不足。
4. 程序在回传前同步创建并写 JSON/PGM；日志带互斥锁且每条 flush。输出缓存失效、写盘、部分线程等待没有独立计时。因此 `result_wait_ms - bpu_ms - post_ms - import_ms` 只是未归因的剩余耗时，不能全算排队。
5. 当前 e2e 日志是取帧 API 起至收到结果附近的估算，未包含传感器曝光/VSE 上游驻留时间，且公式重复加了一次 send_ms（约 0.03–0.08 ms）；两组沿用同一实现以保证参数比较口径一致。
6. 源码中固定周期在迟到后仍追赶旧 deadline，会产生追赶发送；退出排空队列时还存在持锁 sleep。这些实现问题值得单独修正和验证，本次参数实验未修改它们。

下一步优先拆分输出缓存失效、文件写入、日志等待和结果返回的计时，然后对照关闭逐帧文件保存/降低日志量。需要证明 BPU 是否饱和时，再采集硬件性能计数或 profiler 数据。

## 复现新配置

在工程根目录运行：

```bash
BOARD_PASSWORD=root FRAMES=300 WARMUP=5 QUEUE_CAPACITY=1 \
CAPTURE_CPUS=2-3 INFERENCE_CPUS=0-7 RT_PRIORITY=0 \
06_deploy/scripts/perf/run.sh
```

原始日志及线程状态保存在 `../logs/scheduling_comparison/`（Git 忽略）；可提交的全量/稳态汇总保存在 [scheduling_comparison_20261007.json](scheduling_comparison_20261007.json)。测试完成后两个服务已退出。
