# 端侧延迟稳定性优化（2026-10-07）

已部署异步文件保存、异步日志、发送节奏修正和细分计时，并将默认启动配置改为 CPU performance、普通调度、单帧在途。当前场景下，三轮最终配置均显著收敛。结果文件仍逐帧保存，不靠关闭输出获得指标改善。

## 对照方法

三组各 3 轮，每轮 600 帧，共 5,400 帧。所有组均使用 `WARMUP=5 QUEUE_CAPACITY=1 CAPTURE_CPUS=2-3 INFERENCE_CPUS=0-7 RT_PRIORITY=0`、同一个 h2 raw-head 模型和 15 Hz 目标。

旧程序与异步程序的顺序为旧/新/新/旧/旧/新，CPU governor 均为 schedutil；随后仅将新程序的 CPU governor 切为 performance，再跑 3 轮。后者是相同新程序上的 CPU governor 对照，但执行顺序不是随机交错，结论限于本次测试环境。

每轮从统计中排除前 5 个实际推理样本，得到每组 1,785 个稳态样本。摄像头 WARMUP 本身不执行模型；全量统计（含启动）也保存在 JSON，未隐藏冷启动。所有测试现场检测数为 0，未覆盖密集目标 NMS 压力、长时间热稳定性或其他并发业务。

`bpu_ms` 仍是 SDK 提交、等待和释放的墙钟耗时，并非硬件利用率。CPU governor 对照使后处理 P99 从 21.215 ms 收敛到 4.381 ms，BPU API P99 从 40.929 ms 收敛到 35.765 ms；这支持 CPU 调频及运行时调度是重要波动来源，但未测量 BPU 纯硬件执行时间、DDR 带宽或实际占用率。

异步组第 3 轮 frame=154 写盘用了 89.730 ms，对应 e2e=41.113 ms；最终组写盘最大 162.603 ms，结果回传仍稳定。写盘确有长尾，移出回传路径能隔离它。旧程序 673.409 ms 尖峰未单独测量写盘，不能断言该帧完全由写盘导致。

## 实现与行为

- 日志采用独立工作线程、容量 1024 的队列，约 100 ms 批量刷新。默认 info，`LOG_LEVEL=debug` 可开启调试；满队列时丢诊断消息并记录数量，正常退出排空。
- 结果 writer 使用容量 8 的预分配队列，复制约 50 KB mask 和检测结果，独立持有数据。socket 回传先于入队；结果对象可立即复用。这里复制的是输出结果，输入 NV12 仍走零拷贝。
- 输出落盘默认 async；sync 仅用于对照，off 可关闭文件保存。后台跟不上时跳过文件快照并计数，不影响已经发送的检测框/mask。正常退出会等待已接受的文件写完。9 轮都验证了 600 JSON + 600 PGM；新程序全部 written=600 dropped=0 errors=0，没有日志队列丢弃记录。
- 采集迟到后重置下一发送时刻，不追赶旧 deadline 产生突发；退出使用条件变量排空，去掉持锁 sleep；收到结果后先归还 VSE 帧，再记录日志。
- `e2e_ms` 改为取帧调用开始至结果接收完成的直接计时，修复 send_ms 重复相加。旧指标重复项约 0.03–0.08 ms，不能解释数十/数百毫秒差异。e2e 不含传感器曝光、上游驻留及发送前等待容量；新增 queue_wait_ms 与 result_interval_ms 补充可见性。
- 推理结果对象循环复用，新增提交/等待/任务释放/输出缓存/文件入队/写盘计时。socket wire format 未改，新增细项仅在本地日志记录。

## 默认运行与取舍

```bash
BOARD_PASSWORD=root FRAMES=600 06_deploy/scripts/perf/run.sh
```

默认 `QUEUE_CAPACITY=1 CAPTURE_CPUS=2-3 INFERENCE_CPUS=0-7 RT_PRIORITY=0 CPU_GOVERNOR=performance SAVE_RESULTS=async LOG_LEVEL=info`。

CPU performance 会修改板端共享 CPU policy（本次频率 1.5 GHz），并在测试退出后保留该 governor；BPU 继续使用 performance（约 996 MHz）。CPU 功耗可能增加，实际功耗未测。使用 `CPU_GOVERNOR=schedutil` 可在下次启动恢复动态调频，`CPU_GOVERNOR=keep` 保持板端当前设置。性能模式不等于禁用温控。
